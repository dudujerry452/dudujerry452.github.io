引子 ​

为了设计课设, 我们需要搞清楚为什么llama管理KV Cache是高效的.

为此, 我们先了解Transformer中的多头注意力, 然后以Qwen2.5-0.5B为例看看真实的模型架构, 最后分析下LLama的设计. 对于熟悉大模型的读者, 可以直接跳到最后一部分观看.

Transformer ​

从原始Transformer架构中, 模型分为编码器和解码器, "[多头注意力] + [加 & 规范化]"反复出现n次.

实际上, 现代LLM几乎全都使用Decoder-Only的架构, 也就是只有解码器部分, "[多头注意力(MHA)] + [加 & 规范化(Add & Norm)] + [逐位前馈网络(FFN)]"总是作为基本块, 并堆叠上百层.

关于这个块, 可以这么解释: MHA输入句子中所有token向量, 计算句子中token两两之间的相关性, 并输出一个标准向量.

接着, 这个向量进行规范化和残差连接保持梯度, 最后穿过一个FFN(或者说, 其实就是一个多层感知机(MLP), 进行进一步思考.

感性的理解是, 多头注意力负责句子中两两token的关系, 逐位前馈网络负责进一步思考.

注意力 ​

注意力包括Q(query, 查询), K(key, 键值), V(value, 值).

不考虑KV Cache , 多头注意力. 对于词向量维度为, 输入n个词向量, 预测第n+1个词向量的任务, 一个注意力层基本上会做以下的事:

  1. 对于每个token , 分别乘上三个矩阵, 得到三个向量, 维度为.

  1. , 否则二者无法点积计算相似度(见下文)
  2. , 因为这是最后输出的维度

  1. 接着, 对句子中每个, 都做上述计算, 按行组合, 就得到三个矩阵. 每一行都代表一个token的Q/K/V信息.

  2. 计算相关性矩阵. 可以看出其维度为, 元素(i,j)恰好是, 是这两个token的相关性.

  3. 屏蔽中所有的元素. 换句话说就是S的上三角. 这样, 模型就不能作弊"偷看"之后的token, 从而学到真正的推理能力. 另外, 还要对每一行进行softmax, 便于后续加权融合.

  4. 计算, 得到的矩阵, 元素(i, k)就将中每个token的第k维, 根据token i与其他token的相关性加权融合, 得到token i第k维的新信息.

  5. 我们只需要这最后一行. 因为只有它融合了其它所有token的信息.

如果只需要最后一行, 为什么还要计算前n-1行?

  1. 我们展示的是推理过程, 而训练时, 模型被输入的是一整篇文章, 每一行都"相当于"真实推理时推导那个token的过程, 因此也要计算Loss比对. 训练时, 前n-1行也要计算的.
  2. 推理的确可以不用计算前n-1行. 不过在现代SIMD处理器上, 只计算一行不一定更快.

通过注意力层, 我们得到了一个维的向量. 接下来, 我们将其送入[加 & 规范化], 处理梯度问题, 接着送入[FFN]. FFN中, 维度先膨胀再缩减, 便于模型更好的进行理解输出. 由于FFN基本就是简单的双层MLP, 也不是本文重点, 不再讲解.

经过上述处理后, 最终, 数据通过称为LLM Head的层, 将映射到字符集数量维度, 用logits选出最可能的那个token(字符)并输出, 这也是为什么网络上大家说大模型本质上是选概率最大的下一个向量.

KV Cache ​

如果说我们的任务总是给定一个句子, 只预测下一个词, 那么上述计算过程似乎很正常.

值得一提的是, 对大模型而言, 输入最初的那段prompt后执行的任务就是"给定一个句子, 只预测下一个词", 特点是在没有任何历史信息的情况下输入大量token, 只输出一个词. 这被称为prefill阶段, 是我们在端侧模型中需要重点优化的部分.

然而, 我们知道很多时候, 任务其实是:

  • 输入一个句子, 预测下面m个词.
  • 具体而言, 就是输入句子, 预测下一个词, 再把这个词放进句子末尾, 将句子输入给自己, 继续预测下一个词, 以此往复. 这也称为自回归阶段.

这时我们注意到, 如果按照上文计算方法, 每次输入的句子计算后, QKV中其实只有最新的一行变化了!

比如输入"我喜欢吃", 模型输出"我喜欢吃苹果", 在计算"苹"时输入了"我喜欢吃", 计算"果"时输入了"我喜欢吃苹". 也就是说, "我喜欢吃"被重复计算了两次! 后续的token越多, 重复计算的次数也越多.

于是, 我们想到可以缓存重复计算的部分. 对于QKV, 自回归阶段我们每次只计算出一行, 将其加到缓存最后一行中. 这样在计算时其他流程不变, 只是不需要每次都计算巨大的QKV了.

然而, 我们还注意到! 每次只取最后一行, 而, 所以也只需要最后一行, 而, 所以也只需要最后一行. 因此, 根本不必缓存, 因为每次只需要最新的一行, 历史用不上. 这也和的含义对应上了, 是跨token(行)的查询, 不跨维度, 因此各token之间是独立的查询.

综上所述, 我们使用KV Cache可以只计算当前token的, , 向量, 大大减少了计算量.

多头注意力&分组多头注意力(选) ​

实践中, 我们发现普通的注意力只能专注一个概念, 不够智能, 且效率很低.

于是我们将原本的QKV按维度拆为几个部分, 每个部分称为Q/K/V头, 这就是多头注意力(multi-head attention, MHA). 推理时, 这些头并行计算, 过程与单头基本一致.

举例而言, 设, . 其中最多的Q头有14个, 于是我们将896分为14份, 每份64维. 为了对齐, 我们让每个头的维度都是64.

于是, 当计算时, 前7个Q头与第一个K头相乘, 再和第一个V头相乘, 得到7个64维的矩阵; 后面7个也一样. 于是, 我们获得14个64维度的向量, 我们将其按维度拼接回去, 恰好得到维向量, 只要再接一个[896, 896]的融合层即可.

其实, 上面讲的是分组查询注意力(grouped-query attention, GQA), . 原本的MHA中, QKV全被拆成了14份, 两两对应. 然而, 实践中发现Q为主导性能的因素, 为了节省计算量, 我们将14个Q头分组对应到2个K/V头上.

总而言之, MHA的概念十分简单, 就是将QKV按维度分成几个部分并行计算.

位置编码(选) ​

K和Q的信息与位置强相关. 比如"我吃了苹果"和"苹果吃了我", 虽然token组成一致, 但意思完全不一样. 因此, 我们需要在计算前对Q和K进行一些处理, 将位置信息融合进去, 这就是位置编码.

位置编码最常用的是旋转位置编码(Rotary Position Embedding, RoPE), 简单来说就是把Q和K头对应的向量两两分组, 看作平面向量, 根据其位置不同旋转不同的角度. 这样, 不同位置的向量之间就有稳定的旋转角度差, 将信息编码进了向量.

块 ​

Qwen2.5每个块包含了一个RoPE编码的GQA, 以及一个SwiGLU FFN. 前者我们熟悉, 后者意思是采用SiLU激活函数的, 带有门控的线性神经网络. 看图, 输入分别进入SiLU激活函数的门控和一个Up-Down的两层神经网络, 在Up层根据门控关闭和调整部分维度, 最后残差连接到注意力输出.

Llama.cpp之KV-Cache ​

首先, 我们必须搞懂Llama的几个抽象. LLama中, 负责KV Cache的数据结构是llama_kv_cache, 继承自llama_memory_i, 在llama-kv-cache.h中定义.

tensor ​

张量. 所有KV Cache都平铺在内存内, 作为一个巨大的张量表. 定义在llama-kv-cells.h:

cpp
   struct kv_layer {                                              
       uint32_t il;                                               
       ggml_tensor * k;                       // 整层的 K tensor  
       ggml_tensor * v;                       // 整层的 V tensor  
       std::vector<ggml_tensor *> k_stream;   // 每个流的 2D view 
       std::vector<ggml_tensor *> v_stream;                       
   };

在llama-kv-cells.cpp中申请:

cpp
  ggml_tensor * k = ggml_new_tensor_3d(ctx, type_k,              
n_embd_k_gqa, kv_size, n_stream);  // :233                       
  ggml_tensor * v = ggml_new_tensor_3d(ctx, type_v,              
n_embd_v_gqa, kv_size, n_stream);  // :234                       
  ...                                                            
  k_stream.push_back(ggml_view_2d(ctx, k, n_embd_k_gqa, kv_size, 
k->nb[1], s*k->nb[2])); // :243 每个流切一个 view

读写通过ggml_view, 用形状和步长决定读取方式, 不进行任何拷贝.

cell ​

一个token所有层的K-V数据都存在大tensor中的一列, 该列称为cell. 换句话说cell索引是跨层共享的. cell数据(大tensor)放在device, 而cell的元数据则放在host侧. 定义在llama-kv-cells.h:

cpp
class llama_kv_cells {
    // ... 
       std::set<uint32_t> used;     // 哪些索引被占用  
   std::vector<llama_pos>  pos;  // cell[t] 的位置  
   std::vector<llama_kv_cell_ext> ext;    // cell[t] 的额外信息(x/y, token id)                                                         
   std::vector<llama_pos>  shift;    // cell[t] 的累积位移                                 
   std::vector<seq_set_t>  seq;     // cell[t] 属于哪些 sequence                                                
   std::set<std::pair<llama_pos, uint32_t>>                       
   seq_pos[LLAMA_MAX_SEQ]; // 每sequence: pos->cell 索引
   // ... 
}

stream & sequence ​

sequence: 数学上的一个连续的token流. 比如对应某用户的一个会话.

stream: 工程上动态变化的过程, 对应着一个sequence. 一般以ubatch为单位被处理, 包含缓冲区, 内存地址等动态信息.

大部分时候, 二者意思差不多, 可以混用. 下文不再区分.

ubatch ​

一个完整的请求(batch)可能太大, 当前硬件无法支撑. LLama会将其拆分成当前硬件能处理的大小, 为ubatch(微批次, micro-batch). 实际处理中, 所有计算都是基于ubatch的.

decode ​

一个ubatch做一次前向传播. 处理输入(prefill)和生成阶段都是decode这同一个函数.

slot_info ​

slot_info是一次ubatch中, KV Cache的分配信息.

slot_info包括每个ubatch中的token的stream, cell信息. 对于一个ubatch, 其中每个token所属的stream(strms)及系统为其分配的cell编号都会被记录(idxs).

cpp
    struct slot_info {
        // data for ggml_set_rows
        using idx_vec_t = std::vector<uint32_t>;

        // number of streams: ns = s1 - s0 + 1
        uint32_t s0;
        uint32_t s1;

        std::vector<llama_seq_id> strm; // [ns]
        std::vector<idx_vec_t>    idxs; // [ns]
        // ... 
    }

llama-server中也有slot的概念, 这里和slot_info没关系. server中的slot是一个请求的完整状态(prompt, generation, metrics...), 也就是多少个slot允许同时服务多少个请求, 与seqence等无关.

prepare & apply ​

所有对cell的分配/覆盖操作都不会立刻执行, 而是由prepare算好后存放在slot_info中, 由apply_ubatch执行, 这就保持了原子性.

环形缓冲 ​

有了上述概念, 我们可以接着看最主要的结构. 所有的cell被组织成了一个线性环形的缓冲区. 可以看作一个首尾相接的链表, 节点为cell.

llama_kv_cache中有一个vector<uint32_t> v_heads, 记录某stream从哪个cell索引开始找空cell. slot_info llama_kv_cache::find_slot则使用它来找到下一个空位.

find_slot工作逻辑如下:

  • 从head出发, 沿着环扫描一遍, 找到当前ubatch所需的n个token需要的n个空cell, 否则失败
  • 如果没开启连续模式, 那么就一个个收, 得到的cell是散的; 因为计算attention时是直接用ggml_view拿到的连续整段数据, 所以需要用mask遮蔽所有不属于当前seq的cell
  • cell的分配很像操作系统的页面分配算法, 需要决定哪些页面留在内存中; cell与大tensor也是线性系统与其元素之间的关系.

llama-server ​

也有一些概念:

slot ​

此处slot指的是一次请求对应的处理单元, "请求"仅包含一个sequence的一次前向传播请求, 比如一次prefill或者一次生成请求.

一般而言, 一个slot接受一次请求后, 该请求被打包为单独的batch, 发给llama处理. 内部则拆为ubatch.

连续batching ​

开启连续batching后, server可以接受多个slot发来的请求, 然后将它们打包为一个batch, 跑一次decode. 也就是说, 一次decode可以同时服务多个slot.
